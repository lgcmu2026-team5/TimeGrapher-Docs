# Architectural Drivers

## Glossary

아래 기능 요구사항 전반에서 사용되는 도메인 용어는 통합 [Glossary](Milestone1_6-Glossary.md)에 정의되어 있다 — **도메인 용어** 참조.

## Functional Requirements

### G01 · Watch-Position Testing
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-01-01 | mandatory | 시계 자세 측정 시험은 사용자에게 표준 측정 자세에서 기계식 시계를 테스트할 수 있는 기능을 제공해야 한다. |
| FR-01-02 | mandatory | 시계 자세 측정 시험은 GUI를 통해 사용자에게 현재 시계 자세를 제공해야 한다. |
| FR-01-03 | mandatory | 시계 자세 측정 시험은 수평 자세인 CH 및 CB와 수직 자세인 6H, 9H, 3H, 12H로 구성된 표준 자세 세트를 사용자에게 제공해야 한다. |
| FR-01-04 | recommended | 시계 자세 측정 시험은 사용자에게 중간 자세에 대한 지원을 제공하는 것이 권장된다. |
| FR-01-05 | mandatory | 시계 자세 측정 시험은 측정이 진행되는 동안 활성 측정 자세를 사용자에게 명확하게 표시해 주어야 한다. |
| FR-01-06 | mandatory | 시계 자세 측정 시험은 활성 측정 자세와 관련된 측정 결과를 사용자에게 제공해야 한다. |

### G02 · Trace Display
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-02-01 | mandatory | 트레이스 디스플레이는 시간에 따른 일오차(rate deviation) 그래프를 사용자에게 제공해야 한다. |
| FR-02-02 | mandatory | 트레이스 디스플레이는 시간에 따른 진폭(amplitude) 그래프를 사용자에게 제공해야 한다. |
| FR-02-03 | optional | 트레이스 디스플레이는 일오차와 진폭을 세로로 정렬된 단일 그래프 또는 두 개의 별도 그래프 중 하나의 형태로 사용자에게 제공할 수 있다. |
| FR-02-04 | mandatory | 트레이스 디스플레이는 일오차(s/d) 측정값에 대한 평활화(smoothing) 기능을 사용자에게 제공해야 한다. |
| FR-02-05 | mandatory | 트레이스 디스플레이는 시계가 느려지는 상태를 나타낼 때 사용자에게 알림을 제공해야 한다. |
| FR-02-06 | mandatory | 트레이스 디스플레이는 각 그래프에 대한 설명 텍스트 또는 라벨을 사용자에게 제공해야 한다. |
| FR-02-07 | mandatory | 트레이스 디스플레이는 평균값 및 시간에 따라 업데이트되는 이동 평균값을 사용자에게 제공해야 한다. |
| FR-02-08 | mandatory | 트레이스 디스플레이는 두 측정값(일오차 및 진폭)에 대한 장기 요약 정보를 사용자에게 제공해야 한다. |
| FR-02-09 | mandatory | 트레이스 디스플레이는 측정된 진폭이 270°–300° 범위를 벗어날 때 사용자에게 경고 알림을 제공해야 한다. |

### G03 · Rate and Amplitude Stability Over Time (Vario Display)
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-03-01 | mandatory | 바리오 디스플레이는 두 측정값(일오차 및 진폭)의 장기 안정성을 보여주는 정보를 사용자에게 제공해야 한다. |
| FR-03-02 | mandatory | 바리오 디스플레이는 일오차의 최솟값을 사용자에게 제공해야 한다. |
| FR-03-03 | mandatory | 바리오 디스플레이는 일오차의 최댓값을 사용자에게 제공해야 한다. |
| FR-03-04 | mandatory | 바리오 디스플레이는 일오차의 평균값을 사용자에게 제공해야 한다. |
| FR-03-05 | mandatory | 바리오 디스플레이는 일오차의 표준편차를 사용자에게 제공해야 한다. |
| FR-03-06 | mandatory | 바리오 디스플레이는 일오차의 경과된 측정 시간을 사용자에게 제공해야 한다. |
| FR-03-07 | mandatory | 바리오 디스플레이는 일오차의 현재 값을 사용자에게 제공해야 한다. |
| FR-03-08 | mandatory | 바리오 디스플레이는 진폭의 최솟값을 사용자에게 제공해야 한다. |
| FR-03-09 | mandatory | 바리오 디스플레이는 진폭의 최댓값을 사용자에게 제공해야 한다. |
| FR-03-10 | mandatory | 바리오 디스플레이는 진폭의 평균값을 사용자에게 제공해야 한다. |
| FR-03-11 | mandatory | 바리오 디스플레이는 진폭의 표준편차를 사용자에게 제공해야 한다. |
| FR-03-12 | mandatory | 바리오 디스플레이는 진폭의 경과된 측정 시간을 사용자에게 제공해야 한다. |
| FR-03-13 | mandatory | 바리오 디스플레이는 진폭의 현재 값을 사용자에게 제공해야 한다. |
| FR-03-14 | recommended | 바리오 디스플레이는 각 측정 항목의 허용 가능한 최소-최대 범위를 그래프 상에 시각적으로 구분하여 사용자에게 제공하는 것이 권장된다. |
| FR-03-15 | recommended | 바리오 디스플레이는 각 측정 항목의 최소/최대 값을 그래프 상에 시각적으로 구분하여 사용자에게 제공하는 것이 권장된다. |
| FR-03-16 | recommended | 바리오 디스플레이는 각 측정 항목의 평균값을 그래프 상에 시각적으로 구분하여 사용자에게 제공하는 것이 권장된다. |
| FR-03-17 | optional | 바리오 디스플레이는 각 측정 항목의 최대-최소 차이를 사용자에게 제공할 수 있다. |

### G04 · Multi-Position Sequence Display
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-04-01 | mandatory | 다자세 시퀀스 디스플레이는 GUI 내에 시퀀스 표시 화면을 사용자에게 제공해야 한다. |
| FR-04-02 | mandatory | 다자세 시퀀스 디스플레이는 여러 시계 테스트 자세에 걸친 완전한 측정 사이클을 사용자에게 제공해야 한다. |
| FR-04-03 | mandatory | 다자세 시퀀스 디스플레이는 단일 시퀀스 내에서 최대 10개의 테스트 자세에 대한 결과를 캡처하고 검토할 수 있는 기능을 사용자에게 제공해야 한다. |
| FR-04-04 | mandatory | 다자세 시퀀스 디스플레이는 최소한 CH, CB, 6H, 9H, 3H, 12H 자세에 대한 지원을 사용자에게 제공해야 한다. |
| FR-04-05 | mandatory | 다자세 시퀀스 디스플레이는 각 측정 자세에 대한 일오차(rate), 진폭(amplitude), 비트 에러(beat error)를 사용자에게 제공해야 한다. |
| FR-04-06 | mandatory | 다자세 시퀀스 디스플레이는 모든 유효한 측정 자세의 평균값인 X를 사용자에게 제공해야 한다. |
| FR-04-07 | mandatory | 다자세 시퀀스 디스플레이는 가장 큰 측정값과 가장 작은 측정값의 차이인 D를 사용자에게 제공해야 한다. |
| FR-04-08 | recommended | 다자세 시퀀스 디스플레이는 수직 자세와 수평 자세 간의 비교 기능을 사용자에게 제공하는 것이 권장된다. |
| FR-04-09 | recommended | 다자세 시퀀스 디스플레이는 밸런스 휠(balance-wheel)의 불균형 가능성을 파악 가능한 표시기(indicator)를 사용자에게 제공하는 것이 권장된다. |

### G05 · Beat-Noise Scope Display
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-05-01 | mandatory | 비트 노이즈 스코프 디스플레이는 프로그램을 재시작하지 않고 표시할 수 있도록 탭 형식 그래프 패널에 '비트 노이즈 스코프' 탭을 사용자에게 제공해야 한다. |
| FR-05-02 | mandatory | 비트 노이즈 스코프 디스플레이는 서로 연관된 두 개의 뷰인 '스코프 1'과 '스코프 2'를 사용자에게 제공해야 한다. |
| FR-05-03 | mandatory | 비트 노이즈 스코프 디스플레이는 라이브(Live) 모드를 사용자에게 제공해야 한다. |
| FR-05-04 | mandatory | 비트 노이즈 스코프 디스플레이는 재생(Playback) 모드를 사용자에게 제공해야 한다. |
| FR-05-05 | mandatory | 비트 노이즈 스코프 디스플레이는 시뮬레이션(Sim) 모드를 사용자에게 제공해야 한다. |
| FR-05-06 | recommended | 비트 노이즈 스코프 디스플레이는 일시정지 기능을 사용자에게 제공하는 것이 권장된다. |
| FR-05-07 | recommended | 비트 노이즈 스코프 디스플레이는 캡처된 데이터를 앞뒤로 탐색하는 기능을 사용자에게 제공하는 것이 권장된다. |
| FR-05-08 | mandatory | 스코프 1은 시계의 tick/tock 비트 노이즈의 파형 표시 기능을 사용자에게 제공해야 한다. |
| FR-05-09 | mandatory | 스코프 1은 20 ms, 200 ms, 400 ms의 선택 가능한 시간 범위를 사용자에게 제공해야 한다. |
| FR-05-10 | mandatory | 스코프 1은 충분한 측정 시간이 경과한 후 현재 파형 아래에 작은 스트립 형태로 가장 최근의 비트 소리들을 사용자에게 제공해야 한다. |
| FR-05-11 | recommended | 스코프 1은 확대 보기를 위해 누적된 이전 비트 스트립 중 하나를 선택할 수 있는 기능을 사용자에게 제공하는 것이 권장된다. |
| FR-05-12 | optional | 스코프 1은 시인성 향상을 위해 신호를 절대값(\|x\|)으로 표시하는 옵션을 사용자에게 제공할 수 있다. |
| FR-05-13 | mandatory | 스코프 1은 관련 A 및 C 이벤트의 식별 기능과 C 이벤트에 대한 시각적 마커를 사용자에게 제공해야 한다. |
| FR-05-14 | mandatory | 스코프 1은 화면에 표시된 비트 패턴과 관련된 구동각(lift angle)을 사용자에게 제공해야 한다. |
| FR-05-15 | mandatory | 스코프 2는 두 개의 수평 축에 표시되는 tick·tock 비트 노이즈를 사용자에게 제공해야 한다. |
| FR-05-16 | mandatory | 스코프 2는 고정된 20 ms 시간 범위를 사용자에게 제공해야 한다. |
| FR-05-17 | mandatory | 스코프 2는 Σ 컨트롤을 통해 평균화 토글(켜기/끄기) 기능을 사용자에게 제공해야 한다. |
| FR-05-18 | mandatory | 스코프 2는 평균화가 켜져 있을 때 무작위 노이즈를 줄이고 신호의 명확성을 높인 결합된 비트 소리를 사용자에게 제공해야 한다. |
| FR-05-19 | mandatory | 스코프 2는 시계의 진동수(beat number) 및 선택한 간격에 따라 결정되며, 50번의 tick 간격과 50번의 tock 간격 후에 완료되는 측정 사이클을 사용자에게 제공해야 한다. |
| FR-05-20 | mandatory | 스코프 2는 사이클이 끝날 때 화살표를 사용하여 각 수평 축에 평균 진폭을 사용자에게 제공해야 한다. |
| FR-05-21 | recommended | 스코프 2는 고정된 tick/tock 축 할당을 가정하지 않고 평균화된 tick/tock 비트 노이즈 트레이스를 사용자에게 제공하는 것이 권장된다. |
| FR-05-22 | optional | 스코프 2는 10회 또는 20회 간격 측정 후와 같은 중간 평균화 결과를 사용자에게 제공할 수 있다. |

### G06 · Beat Error Display and Diagnostic Trace
| ID | Grade | Requirement |
|----|-------|-------------|
| FR-06-01 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 일오차(rate) 값을 숫자와 단위와 함께 사용자에게 제공해야 한다. |
| FR-06-02 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 진폭(amplitude) 값을 숫자와 단위와 함께 사용자에게 제공해야 한다. |
| FR-06-03 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 비트 에러(beat error) 값을 숫자와 단위와 함께 사용자에게 제공해야 한다. |
| FR-06-04 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 BPH(시간당 진동수) 값을 숫자와 단위와 함께 사용자에게 제공해야 한다. |
| FR-06-05 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 시계의 시간 동작 특성을 나타내는 tick/tock 트레이스 라인을 사용자에게 제공해야 한다. |
| FR-06-06 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 측정값(일오차, 진폭, 비트 에러, BPH)과 tick/tock 트레이스 라인을 동시에 사용자에게 제공해야 한다. |
| FR-06-07 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 시각적으로 구분되는 요소로서의 tick 트레이스 라인과 tock 트레이스 라인을 사용자에게 제공해야 한다. |
| FR-06-08 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 tick/tock 트레이스 라인 사이의 간격을 사용자에게 제공해야 한다. |
| FR-06-09 | optional | 비트 에러 디스플레이 및 진단 트레이스는 트레이스 라인 간격의 허용 범위를 구성할 수 있는 기능을 사용자에게 제공할 수 있다. |
| FR-06-10 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 트레이스 라인 간격에 대해 정의된 허용 범위를 사용자에게 제공해야 한다. |
| FR-06-11 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 트레이스 라인 간격이 허용 범위를 초과할 때 사용자에게 경고를 제공해야 한다. |
| FR-06-12 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 트레이스 라인의 기울기를 사용자에게 제공해야 한다. |
| FR-06-13 | mandatory | 비트 에러 디스플레이 및 진단 트레이스는 트레이스 라인의 기울기가 45도 이상에 도달할 때 결함 상태 표시(fault-state indication)를 사용자에게 제공해야 한다. |

### 용어 설명

아래 시나리오에서 사용되는 지표·단위·표준 용어는 통합 [Glossary](Milestone1_6-Glossary.md)에 정의되어 있다 — **품질 속성·측정 용어** 참조.

### QAS-1 · Performance (Latency) — 소리 입력에서 화면 표시까지
> **한 줄 요약: 소리가 마이크에 들어오면 0.5초 안에 화면에 나타난다.**
>
> Raspberry Pi 5에서 Live로 측정하는 동안 시계 소리가 마이크를 통해 입력 → 분석 → 표시 흐름에 들어오면, 시스템은 처리하여 화면에 표시하고 세 지연 구간을 보고하며, 10분 연속 실행 동안 (1) processing latency p99와 (2) display latency p99를 보고하고 (3) processing+display latency는 **p99 ≤ 500 ms**이어야 한다.

**왜 이 속성인가**
- 플랜이 직접 요구하며, 3구간 분해까지 지정한다: *"Teams shall report capture-to-processing latency, processing-to-display latency, and total end-to-end latency in milliseconds."*
- 이벤트가 도착하고 응답을 **시간**으로 측정 → SAP 정의 그대로 Performance (Latency).

| 요소 | 내용 |
|------|------|
| 자극유발원 | 시계 소리 (외부) |
| 자극 | 마이크로 소리가 들어옴 |
| 대상 | 입력 → 분석 → 표시 - 해당 시점의 타임스탬프 |
| 환경 | Raspberry Pi 5(8 GB)에서 Live 측정 |
| 응답 | 처리하여 화면에 표시하고, 세 지연 구간을 보고함 |
| 응답측정 | 10분 연속 실행 동안: (1) processing latency — p99 (2) display latency — p99 (3) processing + display latency — **p99 ≤ 500 ms** (pass/fail 게이트) |

**측정값 근거**
- **≤ 500 ms** — p99(하위 1% 느린 값)를 Google INP(Interaction to Next Paint) 기준에서 "poor"로 넘어가기 직전 값(good ≤ 200 ms · needs improvement ≤ 500 ms · poor > 500 ms); 최종 디스플레이 갱신의 최대 허용 한계값으로 채택.

**관련 FR** — FR-08-01, FR-12-04, FR-05-03, FR-12-14 (실시간/Live 표시 기능)

### QAS-2 · Availability (Graceful Degradation) — 잡음·약신호 환경
> **한 줄 요약: 잡음 속에서도 신호가 충분할 때는 측정 서비스를 유지하고, 부족하면 "신호 약함"을 표시한 뒤 적절하게 처리한다.**
>
> 잡음이 포함된 열악한 작업 환경에서 잡음 섞인 시계 소리 또는 약한 시계 소리가 잡음 제거·비트 감지 부분에 들어오면, 시스템은 신호를 수용해 제한된 오차 안의 측정값을 내거나, 품질 임계 미만 입력에는 "신호 약함"을 표시하고 적절하게 처리한다. SNR ≥ 30 dB에서 수용된 입력은 감지율 **≥ 95%**이고, 표시 일오차가 **Sim/Playback 기준 일오차에서 ±3 s/d 이내**여야 한다.

**왜 이 속성인가**
- 플랜 원문: *"the system should degrade gracefully when the signal is weak, noisy, or partially missing, rather than producing unstable or misleading outputs."* — graceful degradation은 SAP에 수록된 **Availability 전술**.
- 임계 이상에서는 허용오차 내 감지·측정을, 임계 미만에서는 "신호 약함" 상태로 낮추는 게이트 — 둘 다 **악조건에서도 올바른 서비스를 계속 제공하는 능력** → Availability.

| 요소 | 내용 |
|------|------|
| 자극유발원 | 주변 잡음이 포함된 시계 소리 / 약한 시계 소리 (외부) |
| 자극 | 잡음이 섞이거나 신호가 약하게 들어옴 |
| 대상 | 잡음 제거 / 비트 감지 부분과 신호 품질 표시 |
| 환경 | 주변 잡음이 포함된 열악한 작업 환경 or Sim/Playback 입력에 보정된 잡음을 일정 SNR로 주입한 데이터 |
| 응답 | 사용 가능한 잡음 입력은 수용해 제한된 오차 안의 측정값을 내고, 품질 임계 미만 입력에는 "신호 약함"을 표시하고 적절하게 처리 |
| 응답측정 | 생성기의 알려진 스케줄과 기준 일오차 대비, 1,000비트 이상: SNR ≥ 30 dB인 수용 입력은 감지율 ≥ 95%, 표시 일오차와 기준 일오차의 절대 차이 ≤ 3 s/d; 임계 미만 입력에는 "신호 약함"을 표시하고 적절하게 처리 |

**측정값 근거**
- **30 dB** — 팀 마이크로 실측한 최악 클린 녹음(9개, 30–51 dB)중 제일 심한 조건 — 의도적 잡음 주입으로만 도달; 잠정값.
- **±3 s/d** — 표시된 일오차가 Sim/Playback의 기준 일오차에서 벗어날 수 있는 허용 폭. 폭은 가장 엄격한 Witschi 등급 대역(Chronometer −2…+6 s/d)의 약 절반을 기준으로 둔다. **95%**는 실험으로 확정할 팀 목표.

**관련 FR** — FR-12-08, FR-05-17…18 (잡음 필터링·averaging)

### QAS-3 · Consistency — 표시 간 값 일치
> **한 줄 요약: 화면의 모든 숫자와 그래프는 같은 소스 데이터에서 나온다.**
>
> 평소처럼 측정하는 동안 분석/계산 단계가 하나의 소스 데이터를 여러 그래프·숫자 표시에 전달하면, 한 프레임에 함께 표시되는 모든 것이 그 단일 소스 데이터에서 파생되어 일치하며, 10분 실행 동안 **불일치 0회**이어야 한다.

**왜 이 속성인가**
- 플랜 §Correctness 원문: *"remaining internally consistent across the GUI, derived measurements, and longer-term summaries"* / *"calculations and visualizations are based on the same underlying data."*
- 그 절은 여러 요구의 묶음: 내부 일관성(→ **본 시나리오**)과 잡음 하 사용 가능(→ QAS-2). 본 시나리오는 일관성만 측정하므로 이름도 Consistency — Correctness라 부르면 나머지 부분까지 커버하는 듯한 과대 표기.

| 요소 | 내용 |
|------|------|
| 자극유발원 | 분석/계산 단계 (내부) |
| 자극 | 하나의 소스 데이터가 여러 표시(그래프/숫자)로 전달됨 |
| 대상 | 수치 표시값과 그래프 표시 |
| 환경 | 평소처럼 측정 중 (검증은 Sim/Playback) |
| 응답 | 한 프레임에 함께 표시되는 모든 것이 하나의 소스 데이터에서 파생되어 일치 |
| 응답측정 | 알려진 기준 입력의 10분 실행 동안: 동시에 표시되는 모든 표시에서 **불일치 0회**(표시 반올림 이내); 각 표시는 소스 데이터 식별자를 노출하여 검사 가능 |

**측정값 근거**
- **0** 이 유일하게 말이 되는 목표 — 일관성은 정합성 계열 속성이지 조정 가능한 수치가 아님.
- 각 표시가 어느 소스 데이터에서 왔는지 노출하므로 "0"을 실제로 검증 가능.

**관련 FR** — FR-12-05, FR-06-06, FR-02-07…08 (여러 뷰·요약이 같은 데이터를 표시)

### QAS-4 · Modifiability (Extensibility) — 새 측정/필터/그래프 추가
> **한 줄 요약: 새 그래프·필터·측정값 추가 = 한 곳만 고친다 — 기능당 8 person-days.**
>
> 일정이 촉박한 개발 중에 개발자가 코드베이스에 새 그래프·필터·측정값을 추가하려 할 때, 기존 코드를 뜯어고치지 않고 점진적으로 추가하며, 기존 모듈 변경 **≤ 1개**(공통 부분만) · 기능당 8 person-days이어야 한다.

**왜 이 속성인가**
- 플랜 원문(§Extensibility, Modifiability): *"support the addition of new measurements, filters, graphs, and display modes without major redesign of existing code."*
- **변경 요청**을 **건드리는 코드의 양**으로 측정 → SAP의 Modifiability 일반 시나리오이며, 척도(영향 모듈/위치 수)도 SAP 권장 그대로.

| 요소 | 내용 |
|------|------|
| 자극유발원 | 개발자 |
| 자극 | 새 그래프, 필터 단계, 또는 파생 측정값을 추가하려고 함 |
| 대상 | 측정·표시 기능을 담은 코드베이스 |
| 환경 | 개발 중, 일정이 촉박함 |
| 응답 | 기존 코드를 뜯어고치지 않고 점진적으로 추가함 |
| 응답측정 | 새 그래프/필터/측정값 각각: 기존 모듈 변경 ≤ 1개(공통 부분만), 기능당 8 person-days |

**측정값 근거**
- 3주 일정에 필수 기능 12종 — 좁은 변경 표면이어야만 가능한 일정.
- 마일스톤2/3 일정 (16일) * 조 인원 (6명) / 기능 수 (12) = 8 person-days effort

**관련 FR** — 모든 요구사항

### QAS-5 · Usability — 터치스크린에서 읽기·조작
> **한 줄 요약: 작은 1280×800 터치스크린에서도 핵심 값 3개를 한눈에 읽고 손가락으로 조작한다.**
>
> Raspberry Pi 5의 1280×800(8인치) 터치스크린에서 사용자가 GUI의 측정값을 읽고 모드를 전환할 때, 핵심 측정값을 가독성 있게 표시하고 주요 기능을 터치만으로 조작할 수 있으며, 일오차·비트 에러·진폭 동시 표시 · 영어 대문자 글자 높이 ≥ 2.9 mm · 터치 타깃 ≥ 9 mm를 만족해야 한다. 물리 크기(mm)가 규범 기준.

**왜 이 속성인가**
- 플랜 원문(§Usability and User Purpose): *"The GUI should support ease of use by clearly showing … the calculated values that matter most to the user, such as rate, beat error, amplitude."*
- **사용자** 자극을 **가독성과 과업 시간**으로 측정 → SAP의 Usability 일반 시나리오. 터치 패널은 선택이 아니라 주어진 하드웨어.

| 요소 | 내용 |
|------|------|
| 자극유발원 | 사용자 (시계공 / 측정자) |
| 자극 | 터치스크린에서 측정값을 읽고 모드를 전환함 |
| 대상 | GUI (그래프/수치 표시와 컨트롤) |
| 환경 | Raspberry Pi 5 + 1280×800 터치 디스플레이; 패널 크기 8인치 |
| 응답 | 핵심 측정값을 가독성 있게 표시; 주요 기능을 터치만으로 조작 |
| 응답측정 | 일오차·비트 에러·진폭을 스크롤/확대 없이 동시 표시; 영어 대문자 글자 높이 ≥ 2.9 mm, 터치 타깃 ≥ 9 mm |

**측정값 근거**
- **px가 아닌 mm** — 픽셀 기준은 패널에 따라 합격/불합격이 뒤바뀜; 9 mm는 통용되는 터치 타깃 크기.
- **영어 대문자 글자 높이 ≥ 2.9 mm** — 화면 전체 가시성(SMPTE)·글자 가독성(ISO 9241-303)·터치 조작 여유를 고려해 설계 시야 거리를 보수적으로 50 cm로 채택. 50 cm에서 ISO 9241-303 권장 글자 크기 ≥ 20 arcmin을 환산하면 2.9 mm — 시야 거리 기반 물리 크기로, 패널 해상도와 무관.
  - 계산: 20 arcmin = 20/60° = 0.333° ≈ 0.00582 rad → 글자 높이 = 시야 거리 × 시각 = 500 mm × 0.00582 ≈ **2.9 mm**
  - 본 패널 기준 px 환산 (8″ 1280×800 → √(1280²+800²)/8 ≈ 189 PPI, 1 px ≈ 0.135 mm): 글자 높이 2.9 mm ≈ **22 px**, 터치 타깃 9 mm ≈ **67 px** (참고용 — 규범 기준은 mm)

**관련 FR** — FR-06-06, FR-01-05, FR-04-03, FR-02-06, FR-06-11·13 (한눈에 읽기·포지션 표시·경보)

## 우선순위

ATAM 방식: 각 시나리오에 (**I**중요도, **D**난이도) 쌍을 부여(H/M/L). H/H 시나리오가 아키텍처를 가장 좌우한다.

| 순위 | QAS | 품질 속성 | I | D | 근거 |
|------|-----|----------|---|---|------|
| 1 | QAS-1 | Performance (Latency) | H | H | 결과가 빨리 떠야 하고, Pi 성능이 병목이 될 수 있음 |
| 2 | QAS-2 | Availability | H | H | 실제 사용 환경에서는 잡음이나 약한 신호가 자주 생길 수 있음 |
| 3 | QAS-3 | Consistency | H | M | 같은 측정 결과가 화면마다 다르게 보이면 안 됨 |
| 4 | QAS-4 | Modifiability | H | M | 아직 추가해야 할 기능이 많음 |
| 5 | QAS-5 | Usability | M | M | 작은 터치스크린이라 화면 배치가 제한됨 |

**정렬:** QAS-1과 QAS-2는 장치가 실제로 쓸 만한지에 직접 연결되므로 앞에 둔다. QAS-3과 QAS-4는 결과 신뢰성과 개발 진행을 지키는 항목이라 그다음이다. QAS-5도 중요하지만 위험은 비교적 제한적이다.
