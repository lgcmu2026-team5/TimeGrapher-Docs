# 프로젝트 진행 시나리오 (Milestone 1 기준)

## 1. 프로젝트 컨텍스트

- **아키텍처 문서**: 전혀 없음 (코드만 주어짐)
- **규모**: 약 10K LOC / 6K SLOC — *QCustomPlot 라이브러리 코드 제외 기준*
- **목표**: **기능 추가 — 10개 기능** (functional requirements). *이것이 유일한 과제 목표이며, 향후 유지보수성 개선은 목표가 아니다.*
  - **리팩터링**은 별도 목표가 아니라, 위 10개 기능을 깨끗하게 추가하기 위한 **수단**.
- **핵심 성격**: 이번 프로젝트의 리팩터링은 **"기능 추가를 위한 (준비) 리팩터링(preparatory refactoring)"** 이다. *목표가 아니라*, 특정 기능을 넣기 쉽게 만들기 위한 **국소적 수단**. → 따라서 **기능(묶음)별로** "필요한 경우 해당 영역만 리팩터 → 그 기능 추가"를 반복한다. (전체를 일괄 리팩터한 뒤 일괄 추가하는 게 아니며, 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가 가능하다.)
- **전제**: 규모가 작은 축이라 *전체 Reconstruction을 먼저* 수행하는 순차 접근이 현실적으로 가능. 단, **클래스 단위가 아니라 모듈 단위**로 추상화해 복원한다.

## 2. 진행 시나리오

### Step 1. Reconstruction (as-is 파악)

- 코드에서 현재 구조를 역으로 뽑아내는 **비파괴적 관찰**.
- 산출물: **현재 기능** + **현재 구조**.
  - 현재 구조 = 신규 기능 추가의 *제약(constraint)* 이자 *리팩터링 대상*.
- 비파괴적이므로 요구사항 분석보다 먼저 수행해도 안전하다.
- 추상화 레벨: 모듈/패키지 (≈ 박스 6~12개). 클래스를 그대로 펼치지 않는다.
- **도구**: **Understand**(SciTools)로 진행 — 의존성 그래프·호출 그래프·메트릭으로 구조와 핫스팟을 *정확히* 추출.
  - 수업에서 **LLM의 한계**(환각·누락, 전체 코드베이스의 구조/의존성을 신뢰성 있게 분석하지 못함)를 강조했으므로, 복원의 구조·의존성 사실은 LLM이 아니라 Understand 같은 정적 분석 도구로 확보한다.

### Step 2. 요구사항 분석 → Architectural Drivers 도출

요구사항 분석의 산출물이 곧 **Architectural Drivers**이며, 다음으로 구성된다.

#### 기능 요구사항 (Functional Requirements)

- **이번 과제의 주 드라이버.** 추가할 10개 기능 + 기존 기능 중 *구조를 형성하는 핵심 기능*.
- 각 기능을 *설계를 판단할 수 있을 만큼* 이해·정리하는 것이 M1의 핵심 작업이다 (채점 기준: "기능 요구사항이 잘 이해되고 있는가").
- **10개 기능 분류**: ① 구조를 건드려 *리팩터링이 필요한* 기능 vs *바로 구현 가능한* 기능, ② 구조적 관심사를 공유하는 기능끼리 군집(예: "새 차트 유형 추가" 류 N개). → 이 분류가 아래 Modifiability 시나리오의 "기능 유형"과 리팩터링 범위를 함께 결정한다.

#### 품질 속성 요구사항 (Quality Attribute Requirements)

- Modifiability — **단, 이번 10개 기능 추가에 한정한다** (향후 유지보수 일반화는 목표 아님). 위에서 군집화한 *기능 유형*에 맞춰 **측정 가능한 시나리오**로 표현.
- 예) "〔기능 유형 A〕 추가 시 〔모듈 X〕 한 곳만 수정해 평균 N일 내 통합 가능".
- 추상적인 "유지보수 잘 되게"가 아니라, **이번 10개 기능을 추가할 때 영향이 국소화되도록** 구체화한다.

#### 제약 (Constraints)

- Step 1에서 파악한 기존 아키텍처 구조.

#### 우선순위 (Prioritization)

- 10개 기능 + 품질 속성 간 우선순위 설정.

> ⚠️ **리팩터링의 "왜" = 이 10개 기능을 깨끗하게 추가하기 위해서.** 즉 기능 요구사항이 리팩터링 방향을 견인한다. Drivers에는 *리팩터링 자체*가 아니라, 그것을 정당화하는 _기능 요구사항 + Modifiability 드라이버_가 들어간다. 실제 리팩터링 설계는 Step 4(Approaches)에서 나온다.

### Step 3. 거친 Approaches 스케치 ↔ Risk / Experiment (루프)

선형 단계가 아니라 **반복 루프**다.

1. "이 10개 기능을 추가하려면 기존 구조를 어떻게 바꿔야 하나" — 후보 패턴·전술(notional approaches = preparatory refactoring 설계)을 떠올린다.
2. 드라이버에 비춰 **불확실/위험 지점**을 식별한다. (functional + non-functional 모두)
   - 기능 추가 위험: "기능 〔K〕가 기존 구조 위에서 구현 불가/대규모 변경 필요", "일부 기능의 요구가 불명확", "기능 간 충돌", "QCustomPlot 등 외부 의존성 통합 난이도", "기능 추가가 성능·메모리를 악화"
   - 리팩터링/복원 위험: "테스트 없는 레거시 리팩터링 → 회귀 위험", "기존 구조가 의도한 리팩터링에 저항", "모듈 X를 아직 완전히 이해 못 함"
   - 일정/스코프: "10개 기능 + 리팩터링이 기한 내 미완"
3. 큰 위험을 **기술 실험(스파이크)** 으로 해소한다.
   - 예) "기능 〔K〕를 작은 프로토타입으로 구현해 기존 구조에서 실현 가능한지 확인", "모듈 X를 패턴 Y로 리팩터한 브랜치에서 대상 기능 추가가 그 모듈만 건드리는지 측정", "특성화 테스트를 붙여 동작 보존 확인"
4. 실험 결과로 접근을 **정제**한다 → 1로 되돌아가 루프.

> 리팩터링의 **to-be 설계가 이 루프에서 형태를 잡는다.** Experiment를 설계하려면 최소한 거친 approaches가 먼저 있어야 타깃이 잡힌다.

### Step 4. 최종 Architectural Approaches 확정

- 루프가 안정되면(위험이 받아들일 만해지면), 드라이버에 매핑된 **설계 결정**을 확정한다.
- 이 설계 결정 = **리팩터링 to-be 구조 + 그 위에서의 10개 기능 추가 설계**. → 아키텍처 레벨 설계 내용의 **중심**.
- 각 접근이 *어떤 드라이버(기능 / Modifiability)를 어떻게 만족시키는지* 명시한다.

### (병행) Project Plan

- 위 흐름과 별개로, 실제 **construction 태스크**(기능별: 필요 영역 리팩터 → 해당 기능 추가) · 순서 · 역할 · 일정을 계획에 반영한다.
- 순서 원칙: 기능(묶음)별로 "필요 영역 리팩터 → 해당 기능 추가"를 반복 (전체 일괄 아님; 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가).

## 3. Milestone 1 산출물 매핑

| M1 산출물 | 시나리오 단계 | 핵심 내용 |
|---|---|---|
| 1. Project Plan | 병행 | 역할·태스크·일정, construction 태스크(기능별: 필요 영역 리팩터 → 추가), 실험 계획 |
| 2. Architectural Drivers | Step 2 | **10개 기능** + Modifiability(측정 가능) + 제약 + 우선순위 |
| 3. Risk Assessment | Step 3 | 프로젝트 전반의 functional/non-functional 위험 — **기능 추가(구현 난이도·요구 불명확·충돌·통합), 리팩터링(회귀·저항), 복원(이해 부족), 일정** — 을 확률·영향(H/M/L)으로 |
| 4. Planned Experiments | Step 3 | 불확실한 접근을 검증하는 스파이크 (질문·완료 기준 명시) |
| 5. Architectural Approaches | Step 4 | 드라이버에 매핑된 설계 결정 (리팩터링 to-be + 기능 추가 설계) |

## 4. 리팩터링은 어디에 들어가는가

리팩터링은 한 칸에 들어가지 않고 **측면별로 분산**된다.

| 측면 | 들어가는 곳 |
|---|---|
| 왜 하는가 (동기) | Architectural Drivers (2) — **10개 기능 추가** + 이를 위한 Modifiability 드라이버 |
| 무엇으로 바꾸는가 (to-be 설계) | **Architectural Approaches (5) — 중심** |
| 뭐가 잘못될 수 있나 | Risk Assessment (3) |
| 불확실한 리팩터링 검증 | Planned Experiments (4) |
| 언제·누가·구체 작업 | Project Plan (1) |

## 5. 핵심 원칙 / 주의사항

- **기능 추가를 위한 리팩터링**: 리팩터링은 목표가 아니라 *10개 기능을 쉽게 추가하기 위한 국소적 수단*. **기능(묶음)별로** "필요 시 해당 영역만 리팩터 → 그 기능 추가"를 반복하며, 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가한다.
- **관찰 vs 개입**: Reconstruction은 *관찰(비파괴)* 이라 요구사항 전에 먼저 해도 되지만, Refactoring은 *개입(수정)* 이라 드라이버·요구사항(어떤 기능을 추가할지)을 안 뒤에 한다.
- **M1은 계획 단계**: 실제 코드 리팩터링/기능 추가 실행은 experiment로 검증된 *다음* construction에서. M1 문서엔 "이렇게 복원했고 → 이게 드라이버(10개 기능 + Modifiability)고 → 이렇게 리팩터/설계할 거고 → 위험은 이거, 이렇게 검증한다"까지가 담긴다. (실제 코드 ✕)
- **Approaches ↔ Risk/Experiment는 루프**: 깔끔한 선후가 아니라 공진화. 문서에 확정되는 Approaches는 그 루프의 산출물이라 목차상 뒤(5번)에 온다.
- **viewtype / style 확정은 이후 단계**: 실제 뷰 문서화는 이 루프가 안정된 다음. M1 범위 밖.
