# ADR 002: Adopt a Three-Layer Architecture (App / Platform / Core)

C#/.NET + Avalonia(ADR 001) 위에서, 분석 도메인·OS 입출력·GUI 책임이 섞이지 않게 분리해야 한다. 분석 로직이 UI·OS에 직접 의존하면 변경이 번지고 이식·테스트가 어려워진다.

## Decision
시스템을 **App / Platform.* / Core 3계층**으로 나누고 하향 단방향·비순환 의존만 허용한다.
* **Core** — 분석 도메인만 담당하며 OS·UI를 참조하지 않는다.
* **Platform.*** — OS 오디오 스택을 **Core가 소유한 오디오 입력 인터페이스 뒤에 은닉**한다.
* **App** — GUI와 합성 루트를 담당한다. 구체 OS 분기는 **단일 어댑터 한 곳**으로 격리하고, 빌드 타깃에 따라 플랫폼 구현을 조건부로 바인딩한다(주 배포 타깃은 라즈베리파이 5). 표현 계층은 **MVVM을 채택한다** — View는 ViewModel에 바인딩하고, 사용자 동작은 커맨드로, 상태 변화는 변경 알림으로 전달한다. 다중 탭 그래프 뷰의 활성 탭 렌더링은 Strategy로 분리한다(ADR 006).

## Rationale
* **변경용이성·이식성·시험용이성**: Core 무의존으로 알고리즘을 UI·OS와 분리해 영향 범위를 좁히고, GUI 없이 결정론적으로 테스트한다.
* **관심사 분리**: 폼 상태·커맨드는 ViewModel에, 고빈도 시각화는 활성 탭만 그리는 Strategy 라우팅(ADR 006)에 둔다. Core가 UI와 무관하게 분석 프레임을 산출하므로 App은 표시만 담당한다.
* **MVVM 채택 (vs. MVC 기각)**: 표현 패턴 후보는 MVC(컨트롤러가 뷰를 직접 조작)와 MVVM이었고, 다음 힘 때문에 MVVM을 택한다.
  1. **스택 결(ADR 001)**: Avalonia는 바인딩·커맨드·변경 알림 우선 프레임워크라, 컨트롤러가 위젯을 명령형으로 조작하는 MVC는 프레임워크 결을 거스른다.
  2. **시험용이성**: 상태·명령을 ViewModel에 두면 GUI 없이 단위 테스트할 수 있다. 로직을 뷰에 두는 MVC는 창을 띄워야 검증돼 자동화가 어렵다.
  3. **동시성(ADR 003)**: 분석이 백그라운드 스레드에서 상태를 push하므로, 변경 알림 기반 단방향 "상태→뷰" 갱신이 스레드 경계와 잘 맞는다.
  4. **선언적 활성/명령 상태**: 버튼 활성 여부 등을 상태 파생 속성으로 한곳에 모아, MVC에서 흩어지기 쉬운 명령형 토글을 없앤다.

  기각한 MVC는 위 네 힘 모두에서 불리하다(원본 Qt/C++의 fat-controller 설계가 그 한계를 보여준다).

## Status
Accepted

## Consequences
* 인터페이스·어댑터 보일러플레이트가 증가한다.
* 의존 방향은 문서만으로는 침식되므로 빌드 시점 강제가 필요하다(ADR 007).
* 동시성 격리(ADR 003)·Pipe-and-Filter(ADR 004)·라우팅(ADR 006)의 기반이 된다.
* 표현 계층이 완전한 MVVM에 이르지 못할 수 있다 — 실시간 시작/중지 생명주기 제어는 바인딩으로 표현하기 번거로워 뷰 코드에 남을 공산이 크다. 그래프 뷰도 양방향 바인딩이 아닌 단방향 push 렌더다(ADR 006).
