# 프로젝트 진행 시나리오 (Milestone 1 기준)

## 1. 프로젝트 컨텍스트

- **아키텍처 문서**: 전혀 없음 — 코드만 주어지며, 베이스라인의 아키텍처는 제공되지 않는다.
- **규모**: 약 10K LOC / 6K SLOC — *QCustomPlot 라이브러리 코드 제외 기준*. 비교적 작은 규모다.
- **목표(두 축)**
  - **기능 요구사항**: 필수 **10개 기능** 추가.
  - **품질 요구사항**: 추가·기존 기능을 둘러싼 **품질 속성**(성능, 수정용이성 등)의 개선. → *기능에만 치우치지 말 것.* (교수 피드백: "컨텍스트가 기능에 너무 집중되어 있다." 기능 주변에는 항상 품질 요구사항이 따라온다.)
- **교육적 목표(가장 중요)**: 이 스튜디오 프로젝트는 결과물 자체보다 **소프트웨어 아키텍처 실천**을 연습하기 위한 *수단*이다 — 품질 속성 요구사항 도출, 전술(tactics) 선택, 트레이드오프 논의, 기술 위험 탐색·해소 등. "모든 기능 + 멋진 GUI를 갖춘 킬러 제품"을 만드는 것이 목적이 아니라, **아키텍처 관련 활동을 제대로 이해하는 것**이 목적이다.
- **현실 목표(데모)**: 5개 팀이 같은 과제를 구현하고 최종 **데모**를 한다. **데모 중 깨지지 않고 잘 동작하는 제품**으로 고객(Dan·Steve·Jason)을 만족시키는 것은 당연한 전제다. (교육 목표와 별개로 반드시 충족.)
- **리팩터링의 위치**: 리팩터링은 그 자체가 목표가 아니라 **더 나은 코드 구조**로 기능을 깨끗하게 추가하기 위한 *수단*이다. → 따라서 **기능(묶음)별로** "필요한 영역만 리팩터 → 그 기능 추가"를 반복한다. (전체를 일괄 리팩터한 뒤 일괄 추가하는 게 아니며, 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가 가능.)

## 2. 진행 시나리오

### 사전 작업. 베이스라인 코드 파악 (as-is 이해) — *비공식 · 비산출물*

- 신규 기능을 그 위에 올릴 **출발점**으로 기존 코드를 이해한다. 단, **이것은 마일스톤 산출물이 아니다.**
- **방법(교수 권고)**: 코드에서 구조를 도구로 자동 추출하기보다 **IDE에서 코드를 직접 열람·탐색**한다. 규모가 작으므로 한 줄씩 정독하기보다 **훑어보며 구조를 파악**하고, 필요하면 **직접 몇 개의 박스로** 정리하는 편이 도구를 돌리는 것보다 더 유용하다.
- **왜 도구 자동 추출에 의존하지 않나**: 코드에서 구조를 기계적으로 뽑으면 박스가 너무 많은 *white noise* 다이어그램이 나온다. 도구는 코드의 *아키텍처적 중요도*(어떤 모듈이 구조적으로 핵심이고 어떤 게 단순 유틸인지)를 구분하지 못하기 때문이다. 거기서 의미 있는 다이어그램으로 정제하려면 큰 노력과 반복이 들고, **마일스톤에 직접 도움이 되지 않는다.** → 도움이 될 때만 가볍게, 시간을 많이 쓰지 않는다.
- **Understand 도구**: 사용은 *선택사항*. 기술부채/위반 자동 분석은 이번 평가에 필요하지 않다. (실제로 돌려본 기술부채 분석은 *VS 설치 미감지* 설정 오류로 정상 동작하지 않았고, 그 결과 "위반 0 / 기술부채 0" 수치 자체가 무의미했다.) 구조·의존성 이해는 **직접 읽기**로 확보한다.
- **우리가 작성할 아키텍처 문서는 "우리 솔루션"의 것**: M2·M3에서 요구되는 아키텍처 기술서는 **베이스라인이 아니라, 기존 위에 추가·재구조화한 우리 솔루션**을 대상으로 한다. 베이스라인 아키텍처를 문서화하는 것은 M1·M2 요구사항이 아니다.

### Step 1. 요구사항 분석 → Architectural Drivers 도출

요구사항 분석의 산출물이 곧 **Architectural Drivers**이며, 다음으로 구성된다.

#### 이해관계자 / 고객 (Stakeholders)

- **Stakeholder** = 프로젝트에 관심을 가진 모든 사람 (일반 용어).
- **고객(Customer)**: **Dan · Steve · Jason** (solvent 측). 제품을 받는 고객.
- **Dan의 두 역할**: 베이스라인 구현에 대한 **기술 컨설턴트**이자 동시에 **고객**.

#### 기능 요구사항 (Functional Requirements)

- **이번 과제의 주 드라이버.** 추가할 10개 기능 + 기존 기능 중 *구조를 형성하는 핵심 기능*.
- 각 기능을 *설계를 판단할 수 있을 만큼* 이해·정리하는 것이 M1의 핵심 작업이다 (채점 기준: "기능 요구사항이 잘 이해되고 있는가").
- **10개 기능 분류**: ① 구조를 건드려 *리팩터링이 필요한* 기능 vs *바로 구현 가능한* 기능, ② 구조적 관심사를 공유하는 기능끼리 군집(예: "새 차트 유형 추가" 류 N개). → 이 분류가 아래 Modifiability 시나리오의 "기능 유형"과 리팩터링 범위를 함께 결정한다.

#### 품질 속성 요구사항 (Quality Attribute Requirements)

- **성능(Performance)·수정용이성(Modifiability)** 등을 **테스트·측정 가능한 시나리오**(자극 → 응답 → 응답 측정값)로 표현한다.
- Modifiability — 위에서 군집화한 *기능 유형*에 맞춰: 예) "〔기능 유형 A〕 추가 시 〔모듈 X〕 한 곳만 수정해 평균 N person-day 내 통합 가능". 추상적인 "유지보수 잘 되게"가 아니라 **이번에 추가할 기능 유형을 넣을 때 영향이 국소화되도록** 구체화.
- **작성 절차(교수 권고)**: 고객에게 "QA 요구사항을 주세요"라고 하면 잘 나오지 않는다. → **우리가 먼저** 합리적이라 생각하는 *측정 가능한* 시나리오(값 포함)를 짧은 문장으로 작성한 뒤, 고객에게 **"이게 맞습니까? 바뀌어야 할 값이 있습니까?"** 로 **검토**받는다. (고객은 생성보다 검토를 잘한다.) → **가능한 한 빨리 서면으로 확보**(마감 전까지).
- **응답 측정값의 주관성에 대해**: "10 person-day" 같은 값이 주관적으로 보이는 것은 흔한 지적이다. 그러나 *노력(effort)* 은 실제로 **측정 가능**하다 — 나중에 새 변경 요청이 들어오면 투입 시간을 재면 된다. 합리적 값을 정하는 데는 조직/팀 경험이 필요하며(숙련된 아키텍트는 "이 환경·팀에서 10 person-day에 무엇이 가능한지" 감이 있다), 플러그인을 쉽게 해 주는 설계(예: micro-kernel 패턴)가 그 값을 달성 가능하게 만든다.

#### 제약 (Constraints)

- **하드웨어**: **라즈베리파이 5(Raspberry Pi 5)** 에서 동작해야 한다.
- **OS**: **윈도우/리눅스 양쪽**에서 실행되어야 한다 (크로스 플랫폼).
- (+ 사전 작업에서 파악한 기존 구조도 신규 기능의 제약이 된다.)

#### 우선순위 (Prioritization)

- 10개 기능 + 품질 속성 간 우선순위 설정 (H/M/L).

> ⚠️ **리팩터링의 "왜" = 이 10개 기능을 깨끗하게 추가하고 품질 속성을 만족시키기 위해서.** Drivers에는 *리팩터링 자체*가 아니라, 그것을 정당화하는 _기능 요구사항 + 품질(Modifiability·Performance) 드라이버_가 들어간다. 실제 리팩터링 설계는 Step 2의 루프에서 형태를 잡아 Step 3에서 *고려 중인* 접근으로 정리하며, 최종 확정은 M2·M3에서 이뤄진다.

### Step 2. 거친 Approaches 스케치 ↔ Risk / Experiment (루프)

선형 단계가 아니라 **반복 루프**다. (※ 이는 단순한 위험 주도 과정이며, **ADD(Attribute-Driven Design)를 따르는 것이 아니다** — ADD는 읽거나 적용할 필요 없음.)

1. "이 10개 기능 추가 + 품질 목표 달성을 위해 기존 구조를 어떻게 바꿔야 하나" — 후보 패턴·전술(notional approaches)을 떠올린다.
2. 드라이버에 비춰 **불확실/위험 지점**을 식별한다. **위험 = 물음표** — "이 아이디어/전술이 통할지 모르겠다"는 지점. (functional + non-functional 모두)
   - 기능 추가 위험: "기능 〔K〕가 기존 구조 위에서 구현 불가/대규모 변경 필요", "일부 기능 요구가 불명확", "기능 간 충돌", "QCustomPlot 등 외부 의존성 통합 난이도", "기능 추가가 성능·메모리를 악화".
   - 리팩터링 위험: "테스트 없는 레거시 리팩터링 → 회귀 위험", "기존 구조가 의도한 리팩터링에 저항", "모듈 X를 아직 완전히 이해 못 함".
   - 일정/스코프: "10개 기능 + 리팩터링이 기한 내 미완".
3. 큰 위험을 **기술 실험(스파이크 / 프로토타입 / proof-of-concept)** 으로 해소한다. 두 형태가 있다.
   - (a) **아이디어 검증**: "기능 〔K〕를 작은 프로토타입으로 구현해 기존 구조에서 실현 가능한지 확인", "성능 2x 개선을 위해 멀티스레딩을 적용한 프로토타입을 만들어 테스트".
   - (b) **대안 비교**: 두 옵션 중 무엇이 나은지 모를 때 둘 다 만들어 데이터로 선택. 예) "오디오 데이터를 buffer에서 받기 vs stream으로 받기 — 양쪽 프로토타입의 성능·정확도를 측정해 하나를 선택".
   - 실험은 **템플릿**에 따라 정보를 기록한다 (질문·완료 기준 명시).
4. 실험 결과로 접근을 **정제**한다 → 1로 되돌아가 루프.

> 리팩터링의 **to-be 설계가 이 루프에서 형태를 잡는다.** Experiment를 설계하려면 최소한 거친 approaches가 먼저 있어야 타깃이 잡힌다.

### Step 3. 최종 Architectural Approaches

- 루프가 안정되면(위험이 받아들일 만해지면), 드라이버에 매핑된 **설계 결정**을 정리한다.
- **M1 범위**: 채택을 *고려 중인* 아키텍처 접근을 **언급**하는 수준이면 충분하다(교수 권고). 최종 확정·뷰 문서화는 M2·M3 단계.
- 이 설계 결정 = **리팩터링 to-be 구조 + 그 위에서의 10개 기능 추가 설계** → 아키텍처 레벨 설계 내용의 **중심**. 각 접근이 *어떤 드라이버(기능 / 품질)를 어떻게 만족시키는지* 명시한다.

### (병행) Project Plan

- 위 흐름과 별개로, 실제 **construction 태스크**(기능별: 필요 영역 리팩터 → 해당 기능 추가) · 순서 · 역할 · 일정을 계획에 반영한다.
- 순서 원칙: 기능(묶음)별로 "필요 영역 리팩터 → 해당 기능 추가"를 반복 (전체 일괄 아님; 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가).

## 3. Milestone 1 산출물 매핑

> 교수가 권한 M1 문서 구조: **(0) Introduction / Project Context → (1) Requirements(기능 + 품질) → (2) Risks & Experiments → (3) Architectural Approaches(고려 중인 것 언급)**. 베이스라인 아키텍처 문서/다이어그램은 요구 대상이 아니다.
>
> *위 (0)~(3)은 교수가 말한 **4항목 문서 골격**이고, 아래 표의 0~5번은 이를 **6개 산출물**로 펼친 별도 번호다 (Requirements=Architectural Drivers(2), Risks & Experiments=Risk Assessment(3)+Planned Experiments(4), Approaches=(5); Project Plan(1)은 병행 항목). 이하 본문·§4의 괄호 번호는 모두 **아래 표 번호**를 가리킨다.*

| M1 산출물 | 시나리오 단계 | 핵심 내용 |
|---|---|---|
| 0. Introduction / Project Context | §1 | 프로젝트 맥락(요약), 목표 두 축(기능 + 품질), 고객 |
| 1. Project Plan | 병행 | 역할·태스크·일정, construction 태스크(기능별: 필요 영역 리팩터 → 추가), 실험 계획 |
| 2. Architectural Drivers | Step 1 | **10개 기능** + 품질(Modifiability·Performance, 측정 가능) + 제약 + 우선순위 |
| 3. Risk Assessment | Step 2 | functional/non-functional 위험 — **기능 추가(구현 난이도·요구 불명확·충돌·통합), 리팩터링(회귀·저항), 코드 이해 부족, 일정** — 을 영향·확률 **H/M/L**로 |
| 4. Planned Experiments | Step 2 | 불확실한 접근을 검증하는 스파이크 (질문·완료 기준 명시) |
| 5. Architectural Approaches | Step 3 | 드라이버에 매핑해 *고려 중인* 설계 접근 (리팩터링 to-be + 기능 추가 설계) |

> **Risk 순위 표기(교수 권고)**: 영향·확률은 **H/M/L**(필요 시 N/A 포함)로 표기하는 것을 권장한다. 숫자(0~10 등) 점수도 각 값의 근거를 정당화할 수 있다면(일기예보 "30%"처럼 객관적 수치가 가능한 경우) 허용되지만, 본 프로젝트에선 "왜 7이 아니라 8인가"를 설명하기 어렵다. → 단순해서 정당화가 쉬운 **H/M/L**을 쓴다 (위험관리 문헌의 권고). 순위는 *영향 × 확률* 두 축으로 본다.

## 4. 리팩터링은 어디에 들어가는가

리팩터링은 한 칸에 들어가지 않고 **측면별로 분산**된다.

| 측면 | 들어가는 곳 |
|---|---|
| 왜 하는가 (동기) | Architectural Drivers (2) — **10개 기능 추가** + 이를 위한 품질(Modifiability·Performance) 드라이버 |
| 무엇으로 바꾸는가 (to-be 설계) | **Architectural Approaches (5) — 중심** |
| 뭐가 잘못될 수 있나 | Risk Assessment (3) |
| 불확실한 리팩터링 검증 | Planned Experiments (4) |
| 언제·누가·구체 작업 | Project Plan (1) |

## 5. 핵심 원칙 / 주의사항

- **기능 추가를 위한 리팩터링**: 리팩터링은 목표가 아니라 *기능을 쉽게 추가하기 위한 국소적 수단*. **기능(묶음)별로** "필요 시 해당 영역만 리팩터 → 그 기능 추가"를 반복하며, 구조적 문제가 없는 기능은 리팩터링 없이 바로 추가한다.
- **베이스라인 분석은 비산출물**: 기존 아키텍처를 도구로 자동 추출·문서화하는 것은 M1·M2 요구가 아니며 마일스톤에 직접 도움되지 않는다. 코드 이해는 **직접 읽기**로 확보하고, 자동 분석에 시간을 쓰지 않는다.
- **코드 파악(관찰) vs 리팩터링(개입)**: 코드 파악은 *비파괴적 관찰*이라 요구사항 전에 먼저 해도 되지만, 리팩터링은 *개입(수정)*이라 드라이버·요구사항(어떤 기능을 추가할지)을 안 뒤에 한다.
- **QA 시나리오는 우리가 먼저 → 고객 검토**: 측정 가능한 값으로 우리가 초안을 만들고 고객(Dan·Steve·Jason)에게 검토받는다. **가능한 한 빨리 서면으로 확보.**
- **위험 순위는 H/M/L**: 근거를 정당화할 수 있으면 숫자 점수도 가능하지만, 본 프로젝트에선 정당화가 어려워 3단계(+필요 시 N/A)를 쓴다 — 단순해서 정당화가 쉽다.
- **ADD를 따르는 게 아님**: 위험/실험 과정은 단순하다 — 베이스라인을 출발점으로 요구를 보고, 물음표(위험)를 실험으로 해소.
- **M1은 계획 단계**: 실제 코드 리팩터링/기능 추가 실행은 experiment로 검증된 *다음* construction에서. M1 문서엔 "드라이버(10개 기능 + 품질)는 이것 → 이렇게 리팩터/설계할 것(고려 중) → 위험은 이것, 이렇게 검증한다"까지가 담긴다. (실제 코드 ✕)
- **Approaches ↔ Risk/Experiment는 루프**: 깔끔한 선후가 아니라 공진화. 문서에 확정되는 Approaches는 그 루프의 산출물이라 목차상 뒤(5번)에 온다.
- **우리 솔루션의 아키텍처 문서**: M2·M3에서 만드는 아키텍처 기술서는 베이스라인이 아니라 우리가 만든 솔루션을 대상으로 한다.
- **viewtype / style 확정은 이후 단계**: 실제 뷰 문서화는 이 루프가 안정된 다음. M1 범위 밖.
